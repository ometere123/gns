# GNS v3.1 Production Hardening ADR

Status: proposed for review. No v3.1 production deployment was made.

This decision record is based on milestone main `7bc4a561f50e37cc50fc6248924d6260f4c88aea`, frozen as `gns-v3-milestone`, and the hardening branch `v3.1-production-hardening`.

## Redirect semantics experiment

A disposable `RedirectProbe` was deployed only to StudioNet at `0x61C5e24A19e48e75BBDa940fB9BF2633DA1A62C9`.

- Deployment: `0xe106dd37172a3ae1c862122680b8546fe0efbf4bec229725a446980bbc63d11f`, finalized with successful execution.
- Direct control (`https://httpbin.org/status/200`): `0x435ccd87e9990a2ec0babde82680407b9905c26a088bb47cb956ffa16ffc3cce`; returned status `200`.
- Same-host 302 (`httpbin.org` to `httpbin.org/get`): `0x38bb3780d94ed64fc95c5fa0112c92f3818aaa963ed0484dca83aa295feb66dc`; returned status `200` and the target body.
- Cross-host 302 (`httpbin.org` to `example.com`): `0x71c599f88a3ad542b889e49d18a0ab77490aab059a74548a83905aefbfbc10e2`; returned status `200` and Example Domain HTML.

For both redirect cases, the probe observed an empty effective `response_url`; the cross-host response exposed the final response headers and body but no final destination URL. This establishes that the runtime followed the cross-host redirect and that the current contract cannot validate the final host after the fetch. The official web-access documentation describes response status/body handling but does not specify redirect or effective-URL semantics: [GenLayer Web Access](https://docs.genlayer.com/developers/intelligent-contracts/features/web-access).

The 301/307/308, loop, and malformed-redirect variants were not needed to establish the vulnerability and were not claimed as tested. The disposable probe was removed and no production contract was changed.

### Redirect decision

This is unsafe for source-bound evidence: an authorized URL can act as a redirect trampoline to unrelated content while the contract sees a successful 2xx response. Do not claim redirect safety for the milestone generation.

The recommended v3.1 order is:

1. Verify whether a runtime-supported no-redirect request or final-URL field exists.
2. If neither exists, evaluate a wallet-signed attestation whose signature covers the complete canonical claim payload. Implement this only after proving that the exact Ethereum signature format can be verified by GenVM validators.
3. Until one of those is proven, retain the documented limitation and reject or avoid redirect-dependent evidence sources operationally. A check of the originally requested URL cannot solve this issue.

No GNSAuthenticity redeployment is authorized by this ADR.

## Payment recovery architecture comparison

The invariant is strict: one payment must become either `CONSUMED/SETTLED` or `REFUNDED`, never both. A timeout by itself is not proof that GenLayer did not consume a receipt.

| Option | Trust assumptions | Double-spend resistance | Liveness/failure mode | Current feasibility |
| --- | --- | --- | --- | --- |
| A. Positive cross-chain settlement | A message/proof from GenLayer is accepted by Arc | Strong only if Arc verifies authenticated finality and settlement is terminal before refund | Bridge/message outage can delay settlement; late settlement must be rejected after refund | No verified GenLayer-to-Arc messaging path in this repository; do not assume Hyperlane support |
| B. GenLayer finalization proof on Arc | Arc verifies a trust-minimized GenLayer finality/state proof | Strong if the proof verifier authenticates the exact consumed payment | Proof generation and verifier availability become operational dependencies | No feasible proof verifier has been established for Arc in this pass |
| C. Validator/quorum settlement attestation | Arc trusts a cryptographically verifiable GenLayer quorum statement | Strong only if validator identity, quorum threshold, replay, and finality are verifiable on Arc | Validator-set rotation and attestation delivery must be handled | Adds substantial trust and protocol complexity; not currently available |
| D. Admin/manual recovery | Treasury/admin is trusted to inspect and reimburse safely | Not permissionless; admin must ensure no later consumption or compensate any race | Human response and custody availability are required | Feasible as support, but must be labelled custodial/manual rather than trustless |
| E. Escrow claim/cancel lifecycle | Arc and GenLayer share an authenticated cancellation/settlement protocol | Safe only if cancellation irrevocably prevents later GenLayer consumption, or settlement proves cancellation was not final | Race between cancel/refund and receipt consumption must be solved on both chains | Not safe to implement with the current one-way receipt-consumption design |

### Recovery decision

Permissionless recovery is not safely achievable with the current GenLayer/Arc primitives demonstrated here. Retain the documented limitation. The only immediately feasible improvement is an explicitly manual/admin-assisted recovery policy, which is not trustless and should not be represented as such.

The current router may continue honoring payment-time pricing for unused receipts, but this does not create a refund right. Any future escrow design needs a terminal state machine, authenticated cross-chain settlement/cancellation, replay protection, late-message rejection, and tests for every settlement/refund ordering.

Required changes if a safe design is later approved:

- Arc router: escrow state, terminal `SETTLED`/`REFUNDED` state, authenticated settlement/refund authorization, replay protection, and events/accounting for both outcomes.
- GenLayer registry: settlement or cancellation proof consumption tied to the exact chain/router/transaction/log/payment key, with no ability to consume a refunded payment.
- GNSAuthenticity: none for payment recovery; only a redirect mitigation would require a fresh authenticity deployment and fresh live proof.
- Cross-chain dependency: a verifiable GenLayer finality/message/proof mechanism accepted by Arc, or an explicitly trusted operator.

## Pause/payment race

Today `registrations_paused` blocks both new reservations and `register`, so a valid reservation followed by a successful Arc payment can be stranded if the registry admin pauses before finalization. The pause is a legitimate emergency control, but it creates a user-payment protection problem.

Do not silently change this on the milestone. For v3.1, evaluate two explicit modes:

- hard pause: blocks all new registration finalization, preserving emergency containment;
- settlement pause: blocks new reservations but permits only pre-pause, still-active reservations with an exact matching intent/payment to finalize.

Settlement pause is friendlier to payers but weakens emergency containment if a pre-pause reservation is malicious. It therefore needs explicit admin semantics, reservation-created-at binding, expiry enforcement, and adversarial tests. The choice requires product/security approval; no implementation is recommended in this ADR.

Renewal currently has separate owner/intent/expiry checks and is not blocked by `registrations_paused`; this distinction should remain explicit in any future pause design.

## Proposed v3.1 test matrix

Redirect tests should execute real requests for direct 200, same-host redirect, cross-host redirect, 301, 302, 307/308, loops, malformed locations, and copied attestations at unauthorized destinations. Assertions must include status, body, effective URL availability, and fail-closed source authorization.

Recovery tests should cover normal settlement, normal recovery, settlement-then-refund, refund-then-settlement, duplicate refund, duplicate settlement, expired intent, wrong payer/payment/namespace, replayed receipt, pause races, and concurrent settlement/refund ordering. They must model authenticated cross-chain proofs rather than assume timeout proves non-consumption.

## Recommendation

**RETAIN DOCUMENTED LIMITATION.** The redirect experiment found a concrete runtime source-binding weakness, and no safe permissionless Arc recovery mechanism is available with the currently demonstrated cross-chain primitives. Do not migrate production, redeploy milestone contracts, or merge v3.1 work until the redirect mitigation and payment-recovery design are separately approved and proven.
